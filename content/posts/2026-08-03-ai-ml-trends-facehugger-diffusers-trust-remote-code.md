2026년 8월 3일, The Hacker News가 Hugging Face의 이미지·영상 생성 라이브러리 Diffusers에서 'FaceHugger'라는 이름이 붙은 취약점 3건(CVE-2026-44827, CVE-2026-45804, CVE-2026-44513)을 보도했습니다. 세 취약점의 공통점은 `trust_remote_code` 옵션을 우회해, 사용자가 명시적으로 신뢰하지 않은 원격 코드를 로딩 시점에 실행시킬 수 있다는 점입니다. 겉으로는 평범한 모델/파이프라인 로딩 API처럼 보이는 지점에서 임의 코드 실행(RCE)까지 이어질 수 있다는 게 핵심 위험입니다.

`trust_remote_code`는 Hugging Face 생태계에서 커스텀 모델 클래스나 파이프라인 코드를 저장소에서 그대로 내려받아 실행하도록 허용하는 플래그입니다. 원래 의도는 분명합니다 — 표준 아키텍처에 없는 실험적 모델도 빠르게 써볼 수 있게 하는 편의 기능이죠. 하지만 이 옵션은 태생적으로 "이 코드를 믿습니까?"라는 질문을 사용자에게 떠넘기는 구조입니다. FaceHugger는 바로 그 신뢰 경계를 실제로는 지켜지지 않게 만드는 우회 경로였습니다. 즉 사용자가 `trust_remote_code=False`로 안전하다고 믿고 있어도, 특정 로딩 경로에서는 검증 없이 원격 코드가 실행될 수 있었다는 뜻입니다.

이 사건이 중요한 이유는 세 가지입니다.

1. **공급망 신뢰의 착시**: 많은 팀이 `trust_remote_code=False`만 지키면 안전하다고 가정합니다. 하지만 플래그 자체의 구현에 우회 경로가 있다면, 정책은 지켰는데 실제로는 뚫려 있는 상태가 됩니다. 보안은 옵션값이 아니라 실제 실행 경로 검증으로 확인해야 합니다.
2. **생성 AI 파이프라인의 공격 표면 확대**: Diffusers는 이미지/영상 생성 서비스의 백엔드로 광범위하게 쓰입니다. 모델 로딩 단계의 RCE는 API 서버, 배치 작업, 심지어 로컬 개발 환경까지 침투 경로가 될 수 있어 파급력이 큽니다.
3. **패치 이후에도 남는 숙제**: CVE가 공개되고 패치가 나와도, 이미 배포된 파이프라인·컨테이너 이미지·캐시된 모델 저장소 스냅샷에 취약한 버전이 남아있을 수 있습니다. "패치했다"와 "운영 중인 모든 인스턴스가 패치됐다"는 다른 문장입니다.

실무 팀이 지금 바로 점검할 수 있는 체크리스트는 다음과 같습니다.

- Diffusers 버전을 확인하고, 세 CVE(44827, 45804, 44513)를 수정한 릴리스로 즉시 업그레이드했는지 확인합니다.
- `trust_remote_code`를 어디서 어떤 값으로 쓰고 있는지 코드베이스 전체에서 검색하고, 특히 자동화된 배치/크론 작업에서 이 옵션이 암묵적으로 True로 설정되어 있지 않은지 점검합니다.
- 모델 로딩을 실행하는 서비스는 최소 권한 컨테이너·네트워크 격리 환경에서 돌리는지 재확인합니다. 플래그 하나에 의존하지 않는 방어선이 필요합니다.
- CI/CD에 커스텀 모델 코드가 자동으로 실행되는 단계가 있다면, 그 단계를 사람이 검토한 코드로만 제한하거나 샌드박스에서 격리 실행하도록 바꿉니다.

FaceHugger는 단일 라이브러리의 버그이지만, 교훈은 일반적입니다. 신뢰 플래그는 구현이 완벽할 때만 의미가 있고, AI 파이프라인이 외부 코드를 실행하는 지점은 항상 별도의 방어선(격리, 최소 권한, 버전 고정)으로 이중으로 지켜야 합니다.
