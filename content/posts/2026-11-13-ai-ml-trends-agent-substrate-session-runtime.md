## 도입: 에이전트는 대부분의 시간을 기다린다

에이전트가 실제로 어떻게 움직이는지 떠올려 보면, 쿠버네티스 위에서 돌리기 어려운 이유가 금방 드러납니다. 에이전트는 한 스텝을 실행하고, 셸 명령을 돌리거나 파일을 고치거나 테스트를 호출한 뒤, 다음 스텝까지 밀리초에서 몇 분 동안 기다립니다. 사람의 다음 프롬프트, 도구 결과, 모델 응답을 기다리는 시간이 대부분입니다. 2026년 11월 10일 NVIDIA 기술 블로그에 소개된 오픈소스 **Agent Substrate**는 이 불일치를 정면으로 겨냥합니다.

## 핵심 신호: 세션마다 Pod를 붙잡을 것인가, 지울 것인가

NVIDIA가 지적한 문제는 두 가지 선택지로 압축됩니다. 세션마다 Pod를 하나씩 따뜻하게 유지하면 아무것도 하지 않는 시간에도 compute 비용이 나갑니다. 반대로 턴마다 Pod를 새로 만들면 매 스텝마다 콜드 스타트 비용을 냅니다. 쿠버네티스에서 Pod 하나를 띄우려면 API 서버, admission, etcd, 스케줄러, kubelet, 이미지 pull, 네트워크 설정을 거칩니다. 수 초가 걸리는 것은 몇 주 동안 떠 있는 서비스에서는 괜찮지만, 10밀리초짜리 bash 명령 하나를 실행하고 사라져야 하는 샌드박스에는 너무 느립니다.

Agent Substrate의 해법은 실행 단위를 Pod에서 분리하는 것입니다. 쿠버네티스는 준비된 워커 Pod의 풀을 관리하고, 그 위에 별도의 제어 평면이 대량의 액터(에이전트와 그 실행 환경)를 더 작은 워커 풀에 매핑합니다. 액터가 유휴 상태가 되면 샌드박스(gVisor 또는 microVM)에서 스냅샷을 떠 내고 워커를 반환합니다. 다시 호출되면 비어 있는 아무 워커에나 메모리와 파일시스템 상태를 그대로 복원합니다. 복원은 API 서버나 스케줄러, kubelet을 다시 거치지 않으므로 콜드 스타트 경로가 사라집니다. 발표 자료는 10배 높은 밀도를 주장하지만, 이는 벤더 측 수치라 실제 워크로드에서 재현해 봐야 합니다.

## 왜 지금 나왔나: 세 가지 수요가 겹쳤다

블로그가 든 수요 사례는 세 가지입니다. 첫째, 코딩 어시스턴트입니다. 에이전트가 저장소를 복제하고, 파일을 고치고, 빌드와 테스트를 돌리는 사이에 LLM을 호출하는 패턴이라, 사용자는 턴 사이에도 환경이 유지되고 즉시 응답하기를 기대합니다. 수천 개 세션마다 전용 웜 샌드박스를 둘 수는 없습니다. 둘째, 강화학습 사후 학습입니다. 검증 가능한 보상으로 학습할 때 GPU 트레이너 옆에 코드 샌드박스, 컴파일러, 브라우저, 시뮬레이터 같은 CPU 환경 군단이 붙고, 샌드박스 수요는 배치가 디스패치되는 순간 몰려듭니다. 가장 느린 환경이 다음 배치를 결정하므로 콜드 스타트는 곧 GPU 유휴 시간이 됩니다. 셋째, 연구용 GPU 샌드박스입니다. CUDA 컴파일이나 커널 벤치마크를 위해 에이전트가 GPU 샌드박스를 잠깐 띄웠다 지우는 패턴입니다.

이 세 사례의 공통점은 "잠깐 생겼다 사라지는 격리된 실행 환경이 많이, 빠르게, 공정하게 필요하다"는 것입니다. 쿠버네티스의 Pod 모델은 상시 서비스를 전제로 설계됐기 때문에 이 패턴과 맞지 않습니다.

## 깊이 읽기: 오픈소스 표준 경쟁이라는 맥락

블로그는 에이전트 인프라가 독자 런타임으로 쪼개져 쿠버네티스를 우회하는 흐름을 경계하며, 업스트림에 기여하는 이유를 밝힙니다. 이 프로젝트는 현재 CNCF Sandbox에 기증됐습니다. 여기서 봐야 할 것은 기술 자체보다 **통제 지점**입니다. 에이전트가 쓰는 샌드박스가 어떤 노드에서 어떤 쿼터와 배치 정책을 받는지가 플랫폼 팀의 거버넌스 문제가 됩니다. 블로그가 강조하듯 워커는 여전히 일반 Pod이므로 클러스터 스케줄링, 쿼터, 배치 정책이 그대로 적용됩니다. 보안 관점에서는 세션 스냅샷 자체가 민감 데이터를 담는다는 점을 함께 봐야 합니다. 유휴 세션의 메모리와 파일시스템이 디스크나 객체 저장소에 떨어진다면 그 저장 위치와 암호화, 보관 기간을 정책으로 정해야 합니다.

또 하나는 "대기열이 있어야 한다"는 설계 변화입니다. 블로그가 소개한 업스트림 개선 중 하나는 모든 워커가 바쁠 때 즉시 에러를 내던 동작을 요청 파킹(parking)으로 바꾼 것입니다. 피크 시간의 코딩 어시스턴트나 RL 롤아웃 버스트에서는 다음 턴이 바쁜 순간에 도착할 수 있고, 다른 액터가 곧 워커를 비운다는 점을 고려하면 실패 대신 대기가 맞는 설계입니다. 에이전트 플랫폼을 만드는 팀이라면 "용량 부족이면 실패"와 "용량 부족이면 잠시 대기" 중 어느 쪽이 사용자 경험과 비용에 맞는지 먼저 정해야 합니다.

## 실무 관점: 무엇을 점검하면 되나

- 에이전트 세션의 **유휴 비율**을 먼저 측정하세요. 세션이 실제로 놀고 있는 시간이 길수록 스냅샷 기반 런타임의 이득이 커집니다.
- 콜드 스타트 시간을 스텝당 비용으로 환산하세요. 10밀리초 명령 하나에 수 초가 붙는다면 병목은 실행이 아니라 기동입니다.
- 스냅샷에 들어가는 상태(메모리, 파일, 환경변수, 토큰)를 목록으로 적고, 어떤 항목을 스냅샷에서 제외할지 정하세요. 시크릿이 체크포인트에 남으면 복원 경로가 곧 유출 경로가 됩니다.
- 벤더 수치인 "10배 밀도"는 그대로 믿지 말고, 자기 워크로드에서 같은 조건으로 재측정하세요.

## 결론

에이전트 인프라의 단위는 Pod가 아니라 **세션의 상태**로 이동하고 있습니다. Agent Substrate는 그 전환을 쿠버네티스 안에서 해결하려는 첫 번째 큰 시도이며, 채택 여부는 스냅샷 복원 속도와 상태 보안을 자기 데이터로 검증할 수 있는지에 달려 있습니다.
