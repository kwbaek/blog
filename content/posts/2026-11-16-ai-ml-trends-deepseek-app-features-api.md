## 도입: 검색과 문서 파싱 계층을 직접 짜던 시간이 줄어들고 있다

지금까지 LLM 기반 서비스를 만들 때 가장 손이 많이 가는 부분은 모델 호출이 아니었습니다. 웹 검색 결과를 가져오고, URL 본문을 정리하고, PDF나 오피스 파일을 텍스트로 바꾸고, 민감한 입출력을 걸러내는 주변 계층이었죠. 많은 팀이 이 계층을 검색 API, 파서, 안전 필터를 이어 붙여서 직접 만들었습니다.

2026년 11월 13일 DeepSeek가 발표한 내용은 이 계층을 모델 제공자 쪽으로 가져가겠다는 신호로 읽힙니다. 자사 앱에서 쓰던 기능들을 API 파라미터로 묶어 외부 개발자에게 열었다는 것입니다.

## 핵심 신호: 앱 기능 다섯 가지를 파라미터로 켠다

발표 페이지(api-docs.deepseek.com/news/news261113/)에 따르면 서버가 도구 호출과 문맥 조립을 처리하는 내장 기능은 다음과 같습니다.

- **웹 검색**: 비사고(non-thinking) 모드에서 인용과 함께 웹·이미지를 검색합니다.
- **심층 사고 검색**: 여러 단계의 추론 중간에 페이지를 검색하고 읽습니다.
- **파일 입력**: PDF, 오피스 문서, 이미지를 대화 문맥으로 변환합니다.
- **URL 읽기**: 사용자 메시지에 들어 있는 링크를 자동으로 가져와 답변에 씁니다.
- **안전 검사**: 입력과 출력을 검사하고, 위험이 감지되면 거부 표시를 돌려줍니다.

검색, 페치, OCR, ASR, TTS는 독립 API로도 따로 호출할 수 있습니다. 전체 기능을 한 번에 붙이지 않고 필요한 조각만 골라 워크플로에 넣을 수 있다는 뜻입니다.

## 깊은 분석: 세 가지를 같이 봐야 한다

첫째, **과금 구조가 둘로 나뉩니다.** 토큰 비용 외에 도구 사용료가 별도로 붙습니다. 검색을 여러 번 도는 심층 사고 모드에서는 토큰보다 도구 호출 횟수가 비용을 좌우할 수 있습니다. 직접 만든 파이프라인과 비교할 때 이 항목을 빠뜨리면 단가 비교가 틀어집니다. 공개 단가표가 있으니 실제 호출 로그로 한 번 계산해 보는 것이 좋습니다.

둘째, **공개 서비스에는 안전 검사가 필수입니다.** 발표는 공개용 앱이라면 안전 검사를 켜야 한다고 명시합니다. 동시에 콘텐츠 모더레이션, 해당 모델의 등록 의무, AI 생성물 표기에 대한 책임은 개발자에게 남는다고 적었습니다. 기술이 필터를 제공해도 법적·운영 책임까지 넘어오지는 않는다는 점이 핵심입니다.

셋째, **URL 읽기는 편하지만 신뢰 경계를 흐립니다.** 사용자가 보낸 링크를 서버가 자동으로 가져오면, 그 페이지 안에 적힌 지시문이 모델 문맥에 들어갈 수 있습니다. 내부 시스템이나 민감 데이터를 다루는 에이전트라면, 자동 페치를 켜기 전에 어떤 도메인을 허용할지, 가져온 본문을 도구 실행 권한과 어떻게 분리할지 먼저 정해야 합니다.

## 실무 관점: 무엇을 확인해야 하나

- 기존에 쓰던 검색·파서·안전 필터 중 어느 것을 대체할지 목록부터 만든다.
- 도구 호출 횟수를 로그로 남겨 한 요청당 도구 비용을 계산한다.
- 공개 서비스라면 안전 검사 응답(거부 표시)을 사용자 화면과 로그에서 어떻게 처리할지 정한다.
- 자동 URL 읽기는 도메인 허용 목록과 함께 켠다. 페이지 본문은 데이터로만 취급하고 도구 권한을 주지 않는다.
- 한국어 문서와 표 형식 파일에서 파싱 품질이 어떤지 샘플로 직접 확인한다. 발표에는 정확도 수치가 없었습니다.

## 결론

모델 회사가 검색과 문서 파싱, 안전 검사를 기본 기능으로 가져가면서, 개발 팀의 경쟁력은 그 위에서 무엇을 어떤 권한으로 연결하느냐로 옮겨 가고 있습니다. 편의 기능이 늘수록 비용과 책임의 경계를 먼저 그어야 합니다.
