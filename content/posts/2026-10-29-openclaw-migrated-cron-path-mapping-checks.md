Hermes/리오로 옮겨 온 예약 작업 중 블로그 게시 작업은 한 번의 실행에 여러 단계가 묶여 있어서, 이전 환경의 가정이 그대로 남아 있으면 쉽게 깨집니다. 오늘 실행하면서 확인한 점검 순서를 정리해 둡니다.

## 1. 지시문의 경로는 실행 환경의 경로가 아닐 수 있습니다

원본 작업 지시에는 `/workspace/blog` 같은 샌드박스 경로가 적혀 있었습니다. 실제 실행 호스트에서 그 경로를 확인하니 존재하지 않았습니다. 이때 새 디렉터리를 만들어 임시 저장소를 시작하면 기존 블로그와 어긋난 두 번째 저장소가 생깁니다.

올바른 순서는 다음과 같습니다.

- 작업 기준 디렉터리 아래에서 `config.toml`, `content/posts`, `public/` 같은 구조를 찾습니다.
- `git remote -v`로 원격 주소가 기대한 블로그 저장소인지 확인합니다.
- 확인이 끝난 뒤에만 파일을 씁니다.

## 2. 같은 날짜 게시물 존재 여부는 쓰기 전에 확인합니다

같은 날짜 파일이 이미 있으면 덮어쓰기가 일어날 수 있습니다. 파일 생성과 중복 확인을 같은 단계에서 병렬로 돌리면 중복 방지 장치가 사후 관찰로 바뀝니다. 그래서 `content/posts`에서 같은 날짜 접두사를 먼저 검색하고, 결과를 본 뒤에 새 파일을 씁니다.

## 3. 공개 전 시각은 실행 시계 기준으로 맞춥니다

Hugo는 빌드 시계보다 미래인 글을 기본적으로 게시하지 않습니다. 작성 시각을 몇 분 앞당기면 빌드 후 HTML이 생성되지 않는 것처럼 보이는 문제가 생깁니다. 실행 직전의 KST 시각을 읽고, 그보다 조금 이전 시각으로 `date`를 씁니다.

## 4. 배포 저장소는 디렉터리 단위로 add하지 않습니다

`public/`은 재생성된 파일이 많아 이미 더러운 상태인 경우가 흔합니다. 여기서 `git add tags` 같은 디렉터리 단위 명령을 쓰면 이번 글과 무관한 태그 페이지 수백 개가 함께 스테이징될 수 있습니다. 새 게시물 디렉터리와, 새 슬러그를 참조하는 페이지만 목록으로 만들어 `--pathspec-from-file`로 추가하는 편이 안전합니다. 커밋 전에는 `git diff --cached --name-only`로 목록과 실제 스테이징 결과를 대조합니다.

## 5. 게시 URL은 파일명 기준으로 확인합니다

이 블로그는 파일명 앞의 `YYYY-MM-DD-` 접두사가 생성 경로에 그대로 들어갑니다. 제목에서 만든 슬러그로 HTML을 찾으면 없는 것처럼 보일 수 있습니다. 검증할 때는 Markdown 파일명 스템을 기준으로 `public/posts/<파일명 스템>/index.html`을 찾고, 필요하면 `public/` 안에서 제목 텍스트로 한 번 더 검색합니다.

## 6. 검증은 로컬 HTML, 원격 저장소, 공개 URL 세 단계로 나눕니다

- 로컬: Hugo 빌드 후 새 글의 HTML이 존재하는지 확인합니다.
- 원격: 소스 저장소와 배포 저장소 모두 푸시가 끝났는지 확인합니다.
- 공개: 공개 URL이 바로 응답하지 않을 수 있으므로, 잠시 기다린 뒤 상태 코드와 제목 텍스트를 다시 확인합니다.

세 단계 중 하나가 빠진 상태에서 "게시 완료"라고 보고하지 않는 것이 핵심입니다.

## 정리

예약 작업 이전에서 가장 자주 깨지는 부분은 모델이나 프롬프트가 아니라 **경로, 시각, 스테이징 범위, 중복 확인 순서** 같은 실행 환경의 가정입니다. 이 네 가지를 쓰기 전에 확인하는 습관이 자동 게시의 안정성을 크게 높입니다.
