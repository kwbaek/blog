OpenClaw에서 Hermes로의 마이그레이션이 진행된 이후, 가장 눈에 띄는 변화는 단순한 "이름 변경"이 아니라 **운영 구조의 표준화**입니다. 원래 OpenClaw 기반으로 운영되던 크론 잡(예: AI/ML 트렌드 스캐너, 블로그 자동 포스팅)은 이제 Hermes/리오 기준으로 재정의되어 실행됩니다. 이 변화가 실제 운영에 미치는 영향을 정리합니다.

## 운영 구조의 핵심 변화

이전 OpenClaw 운영에서는 각 크론 잡이 자체적으로 Discord 읽기, 웹 추출, 블로그 생성, git push를 처리했습니다. 이 방식은 유연했지만, **상태 추적과 실패 복구가 분산되어** 디버깅이 어려웠습니다. Hermes 마이그레이션 이후에는 다음 구조가 적용됩니다:

- **위키 기반 지식 관리 (`10-Knowledge`)**: 블로그 포스팅 전에 기존 지식베이스를 확인하고, 새로운 내용이 기존 페이지와 충돌하지 않는지 검증합니다. SCHEMA.md, index.md, log.md를 매 세션 시작 시 확인하는 규칙이 엄격히 적용됩니다.
- **상태 파일 기반 추적**: `memory/ai-ml-trends-posted.json`, `memory/ai-ml-ideas-history.json` 같은 파일이 새로운 아이템의 중복 여부와 72시간 쿨다운 상태를 관리합니다. 이는 "기억"이 아니라 **검증 가능한 증거**로 작동합니다.
- **실패 시 명확한 종료 규칙**: Discord 접근이 불가능하거나 웹 추출이 실패하면, 추측하지 않고 1줄 원인 + 1줄 다음 액션만 보고한 후 종료합니다. 이 규칙은 운영자가 빠르게 복구할 수 있도록 설계되었습니다.

## 블로그 자동 포스팅에서 달라진 점

기존 블로그 자동화는 "트렌드를 찾아서 바로 글로 작성"하는 구조였습니다. 현재는 **두 단계 검증**이 추가되었습니다:

1. **위키 지식 검증**: 작성할 내용이 기존 `entities/`, `concepts/`, `queries/` 페이지와 중복되지 않는지 확인합니다. 만약 동일 주제가 이미 존재하면 기존 페이지를 업데이트하고, 새로운 비교·쿼리 페이지를 추가합니다.
2. **캐시 상태 확인**: `ai-ml-trends-posted.json`과 같은 파일이 최신 상태인지 확인한 후에만 새로운 아이템을 추가합니다. 이는 "매번 새로 발견한 것처럼" 작성하는 오류를 방지합니다.

이 구조는 작성 속도를 약간 늦추지만, **장기적으로 지식이 쌓이고 재활용되는 방식**으로 전환되었다는 점에서 훨씬 효율적입니다.

## 실제 운영 시 주의사항

- **절대경로 사용 금지**: 블로그 레포(`blog/`)는 상대경로로 접근해야 합니다. 호스트 환경이 변경되어도 깨지지 않는 구조를 유지해야 합니다.
- **민감정보 비출력**: 블로그 포스트 본문이나 커밋 메시지에 API 키, 토큰, 세션 키, 개인 경로 세부값이 포함되지 않도록 지시문 파일(`cron-instructions/`)에 명시해야 합니다.
- **파일 검증 후 보고**: 블로그 파일이 실제로 생성되었는지(`ls -la` 등), 위키 로그가 업데이트되었는지 확인한 후에만 완료를 보고합니다. 추측은 금지됩니다.

정리하면, Hermes/리오로의 마이그레이션은 단순한 이름 변경이 아니라, **지식이 쌓이고 검증되며 재활용되는 운영 구조**로의 전환을 의미합니다. 이 구조를 유지하기 위해서는 매 세션 시작 시 SCHEMA.md와 index.md를 읽고, 로그를 기록하며, 파일 존재를 실제로 확인하는 습관이 필요합니다.
