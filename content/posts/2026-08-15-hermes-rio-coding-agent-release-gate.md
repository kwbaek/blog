코딩 에이전트가 빠르게 좋아질수록 “최신 버전으로 올리면 되지 않을까?”라는 유혹도 커집니다. 하지만 Hermes/리오로 크론과 개발 자동화를 운영한다면, 모델이나 CLI 업데이트를 단순한 패키지 업그레이드가 아니라 **작은 Release Gate를 통과해야 하는 운영 변경**으로 취급하는 편이 안전합니다. 특히 파일을 수정하고 셸 명령을 실행하는 에이전트는 출력 품질만 바뀌는 것이 아니라 권한, diff, 테스트, 재시작 이후 상태까지 함께 바뀔 수 있습니다.

### 1. 먼저 작업 계약을 고정하기

Release Gate의 출발점은 대표 작업을 고정하는 것입니다. “코드를 개선해줘”처럼 넓은 프롬프트 하나만 저장하면 버전 간 비교가 어렵습니다. 대신 저장소와 브랜치, 입력 파일, 허용 도구, 성공 조건을 명시한 작업 계약을 만드십시오.

예를 들면 다음과 같습니다.

```text
목표: 특정 모듈의 테스트 실패 1건 수정
허용 경로: src/와 tests/만
허용 작업: 파일 읽기, 패치, 테스트 실행
금지 작업: 비밀 파일 읽기, 원격 push, 운영 DB 접근
완료 조건: 테스트 통과 + diff 설명 + 변경 파일 목록
실패 조건: 원인과 재현 명령을 남기고 변경을 되돌림
```

이 계약은 모델을 구속하기 위한 문서이면서 동시에 회귀검증의 기준선입니다. 같은 작업을 이전 버전과 새 버전에 실행하면 어떤 변화가 실제로 발생했는지 비교할 수 있습니다.

### 2. 결과보다 실행 증거를 비교하기

두 번째는 “성공했다”는 텍스트를 믿지 않고 실행 증거를 수집하는 것입니다. Hermes/리오 크론에서 최소한 `version`, `task_id`, `changed_files`, `diff_stat`, `commands`, `test_result`, `approval_events`, `duration`, `rollback_result`를 남기는 것이 좋습니다. 로그를 모두 장황하게 보관할 필요는 없지만, 나중에 사람이 같은 실행을 재구성할 수 있는 포인터는 있어야 합니다.

판정도 단일 점수로 만들지 마십시오. 테스트가 통과했더라도 변경 파일이 허용 범위를 벗어나면 보류입니다. 시간이 줄었더라도 외부 네트워크 호출이 늘었다면 보류입니다. 코드 품질이 좋아졌더라도 실패 후 이전 상태로 복구하지 못한다면 운영 투입이 아닙니다. **품질·권한·비용·복구성**을 함께 보고 `allow`, `hold`, `rollback` 중 하나를 결정하는 구조가 실전적입니다.

### 3. 무인 크론에는 보수적인 기본값을

사람이 바로 옆에서 diff를 확인하는 개발 세션과, 밤새 실행되는 무인 크론은 같은 정책을 써서는 안 됩니다. 무인 작업에서는 새 버전을 먼저 샌드박스나 별도 worktree에서 실행하고, 외부 전송·배포·실거래·서비스 재시작 같은 부작용은 기본적으로 금지하거나 별도 승인을 요구해야 합니다. 자동화가 실패하면 무리해서 성공 문장을 만들기보다, 입력·마지막 단계·복구 가능 여부를 짧게 보고하는 편이 낫습니다.

권장하는 순서는 다음과 같습니다.

1. 현재 버전과 작업 계약을 기록한다.
2. 기준선 작업 세트를 실행해 결과를 저장한다.
3. 새 버전을 격리 환경에서 같은 작업에 실행한다.
4. diff, 테스트, 권한, 비용, 로그를 비교한다.
5. 기준을 통과한 경우에만 다음 단계로 승격한다.
6. 문제가 있으면 이전 버전과 캐시를 복구하고 원인을 기록한다.

이 패턴은 특정 코딩 에이전트에만 해당하지 않습니다. Hermes/리오의 브라우저 자동화, 리포트 생성, 파일 기반 검색, 외부 API 연동에도 그대로 적용할 수 있습니다. 버전이 올라갈 때마다 모든 것을 다시 검증하라는 뜻이 아니라, 실제로 중요한 작업 계약 몇 개를 고정해 작은 회귀 세트를 계속 돌리라는 뜻입니다.

좋은 자동화는 가장 최신인 자동화가 아닙니다. **무엇이 바뀌었는지 알고, 허용 범위를 지키며, 실패했을 때 되돌릴 수 있는 자동화**입니다. 빠른 에이전트 릴리스 시대에는 이 Release Gate가 생산성을 늦추는 장벽이 아니라, 안심하고 업데이트할 수 있게 해주는 속도 장치입니다.
