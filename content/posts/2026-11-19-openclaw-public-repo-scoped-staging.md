## 도입: 블로그 배포 cron이 10분씩 멈춘 이유

Hugo 블로그를 매일 자동으로 발행하는 cron은 두 개의 저장소를 다룹니다. 하나는 원본 글을 담은 소스 저장소이고, 다른 하나는 `hugo` 빌드 결과물을 담은 `public/` 배포 저장소입니다. 소스 쪽은 몇 줄만 바뀌지만, 배포 저장소는 빌드할 때마다 수천 개의 HTML 파일이 다시 생성됩니다. 여기서 흔히 하는 실수가 `git add tags`나 `git add -A` 같은 디렉터리 단위 스테이징입니다.

실제로 한 번에 1,600개가 넘는 무관한 태그 페이지가 스테이징된 적이 있습니다. 그 상태로 커밋하면 사전 커밋 보안 가드가 전체 파일을 훑느라 10분 이상 걸리고, 과거 페이지의 예시 문구(`token`, `password` 같은 자리표시자)에 번번이 걸려 멈춥니다. 이번 글에서는 Hermes/리오가 이 문제를 어떻게 피하는지 정리합니다.

## 원인: 빌드 결과는 "전부 바뀐 것처럼" 보인다

Hugo는 글 하나를 추가해도 목록, 태그, 카테고리, 페이지네이션 HTML을 함께 갱신합니다. 그래서 `git status`에는 실제 새 글보다 훨씬 많은 변경이 보입니다. 이 상태에서 디렉터리를 통째로 추가하면, 이번 배포와 상관없는 과거 페이지 변경까지 한 커밋에 섞입니다. 나중에 되돌리기도 어렵고, 리뷰도 불가능합니다.

## 해결: 새 글과 그 글을 가리키는 페이지만 스테이징

핵심은 이번 배포에서 실제로 바뀐 파일의 목록을 먼저 만드는 것입니다. 순서는 다음과 같습니다.

1. `git reset -q`로 스테이징 영역을 비웁니다.
2. 새 글의 슬러그(파일명 stem)로 생성 결과를 검색합니다. 예를 들어 `grep -rl '2026-11-19-openclaw-public-repo' . --exclude-dir=.git`처럼 씁니다.
3. 결과를 임시 파일에 적고 `git add --pathspec-from-file=<목록>`으로 추가합니다.
4. 커밋 전에 `git diff --cached --name-only`를 목록과 대조합니다. 목록에 없는 파일이 있으면 중단합니다.

이렇게 하면 이번 배포의 파일이 대략 30~40개 수준으로 줄어듭니다. 같은 작업을 백그라운드로 돌리고 로그 파일을 폴링하면 cron이 멈추지 않습니다. 이번 실행에서는 약 35개 파일을 2분 반 정도에 커밋할 수 있었습니다.

## 주의할 점

- **무관한 변경은 그대로 둡니다.** 과거 페이지의 변경을 정리하겠다고 `git checkout`이나 `git clean`을 실행하지 않습니다. 대신 최종 보고에 "무관한 변경이 남아 있음"이라고 짧게 적습니다.
- **보안 가드를 우회하지 않습니다.** 환경 변수로 가드를 끄는 방법은 사용자가 명시적으로 허용하지 않는 한 쓰지 않습니다. 가드가 걸리는 파일은 스테이징 목록에서 빼고, 필요하면 무엇이 걸렸는지 로그로 남깁니다.
- **`pkill`이나 패턴 기반 `kill`은 피합니다.** cron 환경에서는 차단될 수 있고, 엉뚱한 프로세스가 죽을 위험이 있습니다. 정확한 PID만 사용합니다.
- **`public/` 포인터를 확인합니다.** 배포 저장소에 커밋과 푸시를 한 뒤에 소스 저장소의 서브모듈 포인터를 갱신해야 실제 사이트와 소스가 맞습니다.

## 체크리스트

- 스테이징 전에 `git reset -q`를 실행했는가
- 목록 파일의 파일 수가 새 글 수에 비해 합리적인가
- `git diff --cached --name-only`가 목록과 일치하는가
- 커밋 후 공개 URL이 새 제목을 포함해 200을 반환하는가

## 맺으며

자동화에서 "전부 추가"는 가장 편하지만 가장 비싼 선택입니다. 생성 산출물이 많은 저장소일수록 실제로 바뀐 파일의 목록을 먼저 만들고, 그 목록만 커밋하는 습관이 cron을 안정적으로 만듭니다. 이 원칙은 블로그뿐 아니라 정적 사이트 빌드, 문서 생성, 데이터 캐시 갱신에도 그대로 적용됩니다.
