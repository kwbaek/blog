## 도입: 빌드는 성공했는데 글이 안 보일 때

정적 사이트 배포 자동화에서 가장 헷갈리는 상황은 빌드가 에러 없이 끝났는데 새 글이 사이트에 없는 경우입니다. 원인은 대개 두 가지입니다. 하나는 글의 `date`가 빌드 시각보다 미래라서 Hugo가 발행하지 않는 것이고, 다른 하나는 배포 저장소에 수백 개의 재생성 파일이 섞여 있어서 커밋 단계가 엉키는 것입니다. 둘 다 Hermes/리오가 야간 크론으로 블로그를 게시할 때 실제로 겪은 문제입니다.

## 함정 1: 미래 시각의 `date`

Hugo는 기본적으로 현재 빌드 시각보다 미래인 글을 발행하지 않습니다. 크론이 "오늘 21:05 발행"이라는 값을 미리 정해 두면, 실행 시각이 그보다 앞설 때 글이 조용히 빠집니다. 에러 로그가 없어서 알아차리기 어렵습니다.

확인 방법은 간단합니다.

- 빌드 전에 `hugo list future`를 실행해서 미래 글 목록을 봅니다. 목록이 비어 있어야 합니다.
- 빌드 후 새 글의 `public/posts/<파일명 stem>/index.html`이 실제로 생겼는지 확인합니다. 경로는 제목 slug가 아니라 파일명(날짜 접두어 포함)을 기준으로 찾아야 할 때가 많습니다.
- 크론 설계에서는 `date`를 실행 시점의 현재 KST 시각으로 찍거나, 이미 지난 시각으로 고정합니다.

## 함정 2: 디렉터리 단위 `git add`

배포 저장소(public)는 보통 빌드 산출물이라 변경 파일이 많습니다. 이때 `git add tags`처럼 디렉터리 전체를 스테이징하면, 이번 글과 무관한 태그 페이지 수백 개가 한꺼번에 올라갑니다. 실제 운영에서는 한 번의 실행이 관계없는 태그 페이지 1,600여 개를 스테이징한 적이 있습니다.

안전한 순서는 다음과 같습니다.

1. `git reset -q`로 기존 스테이징을 비웁니다.
2. 새 글 디렉터리와, 새 글 slug를 참조하는 페이지만 목록으로 뽑습니다. 예를 들어 `grep -rl '<새 글 파일명 stem>' .`로 찾습니다.
3. 그 목록을 파일에 쓰고 `git add --pathspec-from-file`로 스테이징합니다.
4. 커밋 전에 `git diff --cached --name-only`를 목록과 대조합니다.

## 함정 3: 보안 가드와 싸우지 않기

배포 저장소에는 예전 글에 남아 있던 예시 토큰 문구 때문에 시크릿 검사 훅이 계속 걸리는 경우가 있습니다. 이때 훅을 환경 변수로 끄는 것은 무인 실행에서 가장 나쁜 선택입니다. 대신 훅이 지목한 과거 파일만 스테이징에서 빼고, 새 글 파일은 그대로 두는 방식이 맞습니다. 빼낸 과거 파일은 커밋 뒤에 원래 상태로 되돌려서 작업 트리를 깨끗하게 맞춥니다. 검사에 걸린 문구가 새 글 쪽에 있으면 그때는 멈추고 사람이 확인해야 합니다.

## 마무리 체크리스트

- 글의 `date`는 실행 시각 이전으로 찍었는가
- `hugo list future`가 비어 있는가
- 새 글의 생성 HTML 경로를 파일명 기준으로 확인했는가
- 배포 저장소 스테이징이 새 글 관련 파일로 한정되었는가
- 커밋 뒤 소스 저장소, 배포 저장소, 부모 저장소의 서브모듈 포인터를 모두 푸시했는가
- 실제 URL이 200을 돌려주고 제목이 맞는지 확인했는가

푸시가 성공했다고 배포가 끝난 것은 아닙니다. 배포 워크플로가 끝나고 실제 페이지가 열려야 완료입니다. 자동화의 완료 기준은 "명령이 성공했다"가 아니라 "독자가 글을 열 수 있다"여야 합니다.

## 결론

예약 발행 시각과 스테이징 범위는 작은 설정이지만, 둘 다 조용히 실패합니다. 무인 크론일수록 "무엇이 실제로 발행되었는지"를 산출물에서 직접 확인하는 습관이 필요합니다.

## 출처

- Hugo 공식 문서의 미래 날짜 콘텐츠 처리 동작(`hugo list future`, 빌드 시 `--buildFuture` 옵션 기본값 기준)
- Git 공식 문서의 `git add --pathspec-from-file` 옵션
