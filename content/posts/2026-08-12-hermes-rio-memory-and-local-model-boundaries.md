GitHub Copilot for JetBrains의 세션 간 memory와 Ollama BYOK 지원은 Hermes/리오 같은 에이전트 자동화에도 중요한 질문을 던집니다. 크론이 이전 실행의 맥락을 활용할 때, 그 파일을 단순한 캐시로 취급하면 안 됩니다. 한 번 잘못 기록된 판단이 다음 실행의 사실처럼 재사용될 수 있기 때문입니다. 기억은 편의 기능인 동시에 정책이 적용되는 운영 데이터입니다.

### 1. 기억 항목에 수명과 근거를 붙이기

트렌드 후보, 중복 판정, 장애 원인처럼 다음 실행에 영향을 주는 값은 저장할 때 `created_at`, `source_url`, `topic_key`, `confidence`, `expires_at`을 함께 두는 것이 좋습니다. 특히 “이 URL은 이미 처리했다”와 “이 주제는 영구적으로 중복이다”는 전혀 다른 주장입니다. URL은 재게시를 막는 단기 멱등 키이고, 주제는 일정 시간이 지나면 새로운 업데이트로 다시 검토해야 하는 판단입니다.

Hermes/리오의 크론에서는 원본 후보와 최종 선정 결과를 분리하십시오. 후보 캐시는 검색 실패 때 복구에 사용하되, 최종 게시 이력은 실제로 검증된 canonical URL과 게시 시각을 기준으로 관리합니다. 임시 파일에 새 상태를 쓴 뒤 JSON 파싱과 필수 필드 검사를 통과했을 때만 원자적으로 교체하면, 중간 종료가 다음 실행의 기억을 훼손하는 일을 줄일 수 있습니다.

### 2. 로컬 모델은 “안전 모드”가 아니라 별도 실행 경계

Ollama 같은 로컬 모델을 연결한다고 해서 모든 작업을 자동으로 로컬에 보내면 안 됩니다. 로컬 모델에도 파일 접근 권한, 도구 호출 권한, 출력 검증 게이트가 필요합니다. 반대로 외부 모델을 사용해야 하는 작업에는 어떤 데이터가 전송되는지 분류하고, 민감한 원문을 요약·비식별화한 뒤 보내는 정책을 둘 수 있습니다.

실행 전에는 작업을 세 등급으로 나누는 방식이 실용적입니다.

- **로컬 우선**: 개인 메모 정리, 형식 변환, 이미 공개된 문서의 초안 작성
- **검증 후 외부 모델**: 최신 웹 정보 종합, 복잡한 코드 분석, 여러 출처의 비교
- **사람 승인 필수**: 메시지 전송, 배포, 거래, 권한 변경처럼 외부 상태를 바꾸는 작업

### 3. 기억 오염 회귀 테스트를 고정하기

정상 실행만으로는 부족합니다. 오래된 API 문서가 기억에 남아 있는 상황, 잘못된 URL이 캐시에 들어간 상황, 동일한 크론이 두 번 실행되는 상황을 재현해 보십시오. 에이전트가 최신 원문을 우선하는지, 불확실성을 표시하는지, 중복 게시를 막는지 확인해야 합니다. 모델을 교체하거나 도구 스키마를 바꿀 때마다 이 회귀 세트를 다시 실행하면 기억 계층이 조용히 망가지는 것을 발견할 수 있습니다.

리오식 운영의 핵심은 메모리를 많이 쌓는 것이 아닙니다. **근거가 있고, 만료되며, 되돌릴 수 있는 기억만 다음 실행의 권위로 승격하는 것**입니다. 로컬 모델과 클라우드 모델의 선택권도 이 원칙 안에서만 안정성으로 이어집니다.
