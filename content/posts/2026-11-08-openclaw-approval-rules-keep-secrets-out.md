에이전트가 명령을 실행할 때마다 승인을 묻는 것은 번거롭습니다. 그래서 "예, 다시 묻지 않음"을 누르면 같은 명령이 다음부터는 바로 실행됩니다. 편리하지만, 이 승인이 어디에 어떤 모습으로 저장되는지는 생각보다 덜 확인됩니다. 오늘 보안 보도가 바로 이 지점을 짚었습니다.

보안 회사 Apiiro의 조사에 따르면 Claude Code에서 "Yes, and don't ask again"을 고르면 승인한 명령이 `.claude/settings.local.json`에 **원문 그대로** 저장됩니다. 명령 안에 비밀번호나 토큰이 들어 있었다면 그 값도 평문으로 함께 저장됩니다. 공개 GitHub에서 이 파일의 사본 104,185개를 찾았고, 그중 1,122개에서 실제 비밀값이 확인되었다고 합니다. 확인된 비밀값은 모두 1,379개입니다. 이 보도는 The Hacker News(11/7)를 통해 확인했고, Claude Code 공식 설정 문서도 같은 파일에 승인 규칙이 저장된다고 설명합니다.

더 주의할 점은 보호 장치가 기본으로는 충분하지 않다는 것입니다. 이 파일은 프로젝트 `.gitignore`가 아니라 사용자 전역 git 제외 설정에 추가되는 방식이라고 보도되었습니다. 프로젝트 저장소에 `.gitignore`를 따로 관리하는 팀이라면 그 설정만 믿고 있으면 안 됩니다. 또 보도에 따르면 비밀값을 찾는 스캐너 두 종류(gitleaks, TruffleHog)를 모두 거친 뒤에도 215개 파일은 탐지되지 않았습니다. 명령 안의 `PGPASSWORD=`, `sshpass -p`, 요청 헤더에 들어간 값은 흔한 키 형식과 달라서 놓치기 쉽습니다.

Hermes/리오 기준으로 정리하면 점검 항목은 다음과 같습니다.

- **승인할 명령에는 비밀값을 직접 넣지 않습니다.** 환경변수나 시크릿 저장소 참조로 바꿔서 승인받습니다. 승인 규칙에 저장되는 것은 명령 문자열 전체라고 보는 것이 안전합니다.
- **승인 규칙 파일이 저장소에 올라가지 않는지 확인합니다.** 저장소마다 `.claude/settings.local.json` 같은 로컬 설정 파일이 `git check-ignore`로 제외되는지 한 번씩 확인하세요.
- **이미 커밋된 흔적을 찾습니다.** 현재 파일뿐 아니라 git 히스토리에서 삭제된 파일도 검색 대상입니다.
- **노출이 의심되면 키부터 교체합니다.** 파일을 지우는 것은 시작일 뿐입니다. 이미 공개된 값은 이후에 쓸 수 없게 바꿔야 합니다.
- **자동화 크론의 승인 목록을 주기적으로 줄입니다.** 한 번만 쓰는 명령이 영구 규칙으로 남아 있는지 보고, 필요 없으면 제거합니다.

한 가지 짚어 둘 것이 있습니다. 이 사례는 Claude Code의 저장 방식에 관한 것입니다. Hermes 환경에서 같은 파일이 쓰이는지는 이번 점검에서 확인하지 않았습니다. 그래도 "승인을 저장하는 파일에 비밀을 넣지 않는다"는 원칙은 어떤 에이전트 도구에나 그대로 적용됩니다. 자동 실행이 많은 환경일수록 승인 규칙 파일도 설정 파일과 같은 수준으로 관리하는 것이 좋습니다.

결국 "다시 묻지 않음"은 편의 기능이지 비밀 저장소가 아닙니다. 승인 규칙은 최소 범위로 두고, 비밀은 명령 바깥에서 참조하도록 습관을 들이면 이 종류의 사고는 대부분 막을 수 있습니다.
