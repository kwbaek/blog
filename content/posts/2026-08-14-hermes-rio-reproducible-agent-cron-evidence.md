AI 연구 재현성 프로젝트가 Hermes/리오 크론에 주는 가장 실용적인 교훈은 간단합니다. **성공했다는 문장보다 성공을 다시 확인할 수 있는 증거 번들이 중요하다**는 것입니다. 무인 크론은 마지막 응답만 보면 그럴듯하게 끝났어도 입력이 오래됐는지, 출처가 바뀌었는지, 모델이 다른 경로를 탔는지, 중간 파일이 반쯤 기록됐는지 알기 어렵습니다. 따라서 결과물과 함께 실행 조건을 남기는 구조가 필요합니다.

### 1. 실행마다 고유한 증거 묶음을 만든다

크론 시작 시 실행 ID를 만들고 입력 시각, instruction 버전, 사용한 모델, 도구 호출 목록, 원본 URL, 최종 산출물 경로를 한 묶음으로 기록하십시오. 트렌드 스캐너라면 후보 수집 → canonical URL 확인 → 본문 검증 → 중복 판정 → 캐시 갱신의 단계별 상태를 남기면 됩니다. 최종 글만 저장하는 것보다 어떤 후보가 왜 탈락했는지까지 보존하는 편이 다음 실행의 재현성과 디버깅에 훨씬 유리합니다.

### 2. 캐시는 사실과 판단을 분리한다

`source_url`, `content_hash`, `topic_key`, `source_date`, `model_version`, `confidence`, `status` 같은 필드를 두고 원본 사실과 에이전트의 판단을 구분하십시오. “이미 처리한 URL”은 짧은 기간의 멱등 키일 수 있지만, “이 주제는 영원히 중복”이라는 뜻은 아닙니다. 같은 주제라도 새로운 수치나 운영 변화가 나오면 다시 평가해야 합니다. 오래된 판단을 최신 사실처럼 재사용하지 않도록 만료 시각과 재검토 조건도 함께 두는 것이 좋습니다.

### 3. 원자적 갱신과 회귀 태스크를 고정한다

새 결과는 기존 캐시를 바로 덮어쓰지 말고 임시 파일에 쓴 뒤 JSON 문법, 필수 필드, URL, 날짜, 중복 키를 검증하십시오. 검증이 통과했을 때만 원자적으로 교체하고, 교체 후 다시 읽어 최신 레코드가 실제로 보이는지 확인합니다. 모델이나 도구 스키마를 바꿀 때는 대표 태스크를 replay합니다. 동일한 입력에서 출처 누락, 잘못된 tool call, 중복 게시, 실패 후 무한 재시도가 발생하지 않는지 확인해야 합니다.

### 4. 게시를 별도의 승인 경계로 둔다

파일 생성 성공과 공개 배포 성공은 같은 상태가 아닙니다. 초안 작성, Hugo 빌드, 생성 사이트 갱신, Git push, Pages 배포를 별도 단계로 기록하고 각 단계의 성공 조건을 분리하십시오. 특히 외부 상태를 바꾸는 push나 메시지 전송은 검증된 원고와 빌드 결과가 있을 때만 진행되어야 합니다. 한 단계가 실패하면 이미 성공한 앞 단계의 산출물을 보존한 채 재개할 수 있어야 합니다.

실전 체크리스트는 다음과 같습니다.

- 입력과 출처의 날짜가 작업 창 안에 있는가?
- 결과에 원본 URL과 검증 상태가 붙어 있는가?
- 캐시가 임시 파일 검증 후 원자적으로 교체됐는가?
- 동일 태스크를 재실행했을 때 중복 게시가 막히는가?
- 모델·도구 변경 후 품질, 비용, 지연, 권한 회귀를 확인했는가?
- 공개 배포 전 빌드와 생성 파일 범위를 확인했는가?

Hermes/리오의 크론을 오래 운영하려면 똑똑한 답변을 모으는 것보다, **다음 실행이 같은 입력과 같은 기준으로 결과를 검증할 수 있게 만드는 것**이 먼저입니다. 재현 가능한 증거 번들은 자동화의 로그가 아니라 운영 자산입니다.
