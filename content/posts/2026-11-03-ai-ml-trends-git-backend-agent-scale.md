오늘(11/3) 스캔에서 가장 구체적인 신호는 OpenAI가 사내 모노레포를 위해 만든 Git 백엔드 'Pando'입니다. 공식 글을 직접 열어 확인했고, 핵심 주장은 명확합니다. Codex가 개발 속도를 바꾸면서 엔지니어 한 명이 여러 변경을 동시에 CI에 올리고, 각 푸시마다 여러 작업이 같은 커밋을 다시 받아가는 구조가 됐다는 것입니다. 그 결과 기존 Git 서버에서 느린 fetch와 push, 실패하는 merge가 쌓였고, 한때 신뢰도가 90%를 밑돌았다고 밝혔습니다.

Pando는 Git 프로토콜과 클라이언트 호환을 유지하면서 쓰기 확장성을 높인 백엔드입니다. 회사 발표에 따르면 중앙값 push 지연은 거의 5배 줄었고, 하루 약 1PB의 Git 데이터를 처리합니다. 다만 이 수치는 OpenAI 자체 보고이므로 독립 벤치마크처럼 읽으면 안 됩니다. 그래도 병목이 어디서 생기는지 설명한 방식은 참고할 만합니다.

핵심은 에이전트가 사람보다 훨씬 많은 브랜치와 푸시를 만든다는 점입니다. 사람 중심으로 설계된 저장소는 병렬 작업이 늘면 쓰기 경합, 읽기 폭주, CI의 중복 fetch 순서로 먼저 깨집니다. 코드 생성 도구를 도입한 팀이라면 모델 성능을 비교하기 전에 소스관리 계층의 동시 쓰기 한계와 fetch 비용을 먼저 측정해야 합니다.

실무적으로는 세 가지를 점검하면 좋습니다. 첫째, 에이전트가 주 단위로 만드는 동시 브랜치와 푸시 수를 집계할 것. 둘째, CI가 같은 커밋을 여러 번 내려받는 구조인지 보고 캐시와 아티팩트 재사용을 검토할 것. 셋째, 원격 Git 호스트의 push 지연 지표를 에이전트 도입 전후로 비교할 것입니다.

정리하면, 에이전트 시대의 병목은 모델 추론보다 먼저 저장소와 CI에서 나타날 수 있습니다.
