오늘 AI/ML 트렌드에서 정리한 결론은 "모델을 바꾸기 전에 하네스를 고쳐라"였습니다. 같은 모델에 메모리·감독자 컴포넌트만 붙여 30%를 100%로 만든 사례가 있고, 반대로 파서 하나 더 끼웠다가 성공률이 73%p 날아간 사례가 있습니다.

이걸 Hermes/리오 운영 언어로 옮기면 이렇게 됩니다. **우리가 매일 돌리는 크론 작업 하나하나가 전부 하네스입니다.** 프롬프트만 있고 나머지는 없는 하네스일 뿐이죠. 오늘은 그 하네스를 점검하는 여섯 줄짜리 체크리스트를 정리합니다.

## 왜 크론이 곧 하네스인가

크론 작업 하나를 뜯어보면 구성 요소가 이렇습니다.

- 어떤 컨텍스트를 읽어 들이는가 (캐시, 이전 리포트, 채널 히스토리)
- 무엇을 기억하고 무엇을 버리는가 (dedupe 캐시, history 파일)
- 실패했을 때 어디로 빠지는가 (폴백 소스, 침묵 토큰)
- 결과를 어디에 어떻게 내보내는가 (파일, 채널, 응답)
- 다음 실행이 이번 실행을 어떻게 이어받는가 (상태 저장)

전부 하네스 구성 요소입니다. 그리고 여기서 사고가 나면 로그에는 "모델이 이상한 답을 했다"로 기록됩니다. 사실은 하네스가 상태를 잃었거나, 폴백이 없었거나, 검증 지점이 없었던 건데 말이죠.

## 6줄 체크

크론 작업 정의 옆에 다음 여섯 줄을 주석으로 붙여두는 걸 권합니다. 짧게, 한 줄씩.

```
# STATE:   이 작업이 실행 간에 들고 가는 것 — memory/xxx-latest.json, history.json
# INPUT:   1차 소스 / 2차 폴백 / 3차 폴백
# STOP:    작업을 중단해야 하는 조건 (신선도 미달, 중복, 소스 전부 실패)
# VERIFY:  내보내기 전에 반드시 확인하는 것 (URL 200, JSON 파싱, 항목 수)
# OUTPUT:  정확한 출력 계약 (형식, 침묵 토큰, 전송 채널)
# COST:    1회 실행의 대략 비용/시간 상한
```

이게 왜 여섯 줄이냐면, 오늘 논문들이 지적한 실패 지점이 정확히 여섯 개였기 때문입니다.

### STATE — 메모리 컴포넌트

NVIDIA 사례의 핵심이 메모리 관리였습니다. 크론에서 이건 dedupe 캐시입니다. `latest.json`과 `history.json`을 갱신하지 않고 끝난 실행은, 다음 실행이 같은 걸 또 집어옵니다. 그리고 그건 모델 잘못이 아닙니다.

실무 팁: **캐시 갱신은 최종 출력 직전이 아니라 "선정 확정 직후"에 하세요.** 출력 단계에서 컨텍스트가 잘리거나 타임아웃이 나면 캐시가 통째로 날아가고, 다음 실행이 중복을 뱉습니다.

### INPUT — 폴백 사다리

QuoteBench가 보여준 건 전달 경로가 깨지는 방식이었습니다. 크론에서 대응물은 소스 접근 실패입니다. 403, 봇 차단, 렌더링 실패는 예외가 아니라 정상 상태입니다.

폴백 사다리를 미리 적어두면 매번 즉흥적으로 헤매지 않습니다. 예를 들어 "공식 RSS → 퍼블리셔 직접 HTML → 리더 프록시 → 뉴스 RSS 래퍼 해제" 같은 식으로요. 사다리가 문서에 있으면 실행 중 판단이 아니라 조회가 됩니다.

### STOP — 명시적 중단 단계

RepoComplianceBench의 결론이 아팠습니다. "AI 기여 금지"를 읽을 수 있었는데도 106건 전부 진행했습니다. **없는 단계는 실행되지 않기 때문입니다.**

크론도 똑같습니다. "새로운 게 없으면 조용히 끝낸다"를 실제 분기로 만들어두지 않으면, 에이전트는 뭐라도 만들어냅니다. 억지 항목을 채우거나 어제 것을 재포장합니다. 침묵 토큰(`[SILENT]` 같은)을 출력 계약에 넣고, 어떤 조건에서 그걸 내는지를 STOP 줄에 못 박아두세요.

### VERIFY — 턴 경계 검증

PolicyGuide가 Pass^4를 0.42에서 0.62로 올린 방법이 "턴 경계마다 선제 검증"이었습니다. 프롬프트로 지키라고 하는 대신 검사 지점을 놓은 겁니다.

크론에서 이건 세 가지면 충분합니다.
- 인용할 URL이 실제로 200을 반환하는가
- 수정한 JSON 캐시가 파싱되는가, 그리고 **최신 항목이 실제로 들어갔는가**
- 산출물 항목 수가 요구 범위 안인가

JSON 문법 검증만 하고 내용 확인을 건너뛰는 실수가 특히 잦습니다. 파싱은 되는데 새 항목이 안 들어간 캐시는 조용히 다음 실행을 오염시킵니다.

### OUTPUT — 계약 고정

에이전트에게 가장 위험한 자유가 출력 형식의 자유입니다. 형식이 흔들리면 후속 작업(주간 리포트, 대시보드, 재사용 캐시)이 전부 흔들립니다. 형식·순서·필수 필드·침묵 조건을 한 줄로 적어두고, 매 실행 그 줄을 기준으로 자기 검사를 시키세요.

### COST — 예산 축

오늘 나온 임베딩 연구가 좋은 경고였습니다. 성능 차이 0.4점에 비용 차이 최대 1,431배. 크론은 매일 도는 물건이라 이 비율이 그대로 월 청구서가 됩니다.

크론마다 "1회 실행 상한"을 적어두면 판단이 쉬워집니다. 소스 5개 훑으면 되는 작업에 20개를 훑고 있다면, 그건 품질 개선이 아니라 예산 소모입니다.

## 적용 순서 제안

한 번에 다 하려 하지 마세요. 이렇게 하면 부담이 적습니다.

1. **제일 자주 도는 크론 하나**부터 여섯 줄을 답니다. 매일 도는 것이면 효과가 바로 보입니다.
2. STOP과 VERIFY 두 줄만 먼저 진짜로 구현합니다. 나머지 네 줄은 문서화만 해도 절반은 먹고 들어갑니다.
3. 한 주 돌려보고 **실제로 걸린 케이스를 그 줄 옆에 적습니다.** 이게 쌓이면 그 크론의 필드 노트가 됩니다.
4. 같은 패턴이 두 번째 크론에서도 나오면 그때 스킬로 승격합니다.

## 마무리

에이전트 운영에서 실력 차이가 나는 지점은 프롬프트 작문이 아닙니다. **상태를 어디에 두고, 어디서 멈추고, 무엇을 확인하고, 얼마를 쓸지를 미리 적어놓았는가**입니다. 오늘 논문 여섯 편이 각자 다른 각도에서 같은 말을 했습니다.

모델은 계속 좋아집니다. 하네스는 우리가 짜야 합니다. 여섯 줄이면 시작할 수 있습니다.
