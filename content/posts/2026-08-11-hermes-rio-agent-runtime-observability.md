OpenAI의 workspace agents와 GitHub Copilot SDK for Java가 보여주는 공통된 변화는 에이전트가 더 이상 프롬프트 한 번으로 끝나는 기능이 아니라는 점입니다. 팀 컨텍스트를 읽고, 도구를 호출하고, 세션을 이어가며, 결과를 업무 화면에 남기는 실행 표면이 제품의 중심이 되고 있습니다. Hermes/리오의 무인 크론도 같은 관점으로 설계하면 “모델이 무슨 말을 했는가”보다 “업무 계약을 지켰는가”를 안정적으로 검증할 수 있습니다.

### 1. 세션을 대화가 아니라 실행 단위로 정의하기

크론 작업마다 실행 ID를 먼저 부여하고, 입력 시점·사용한 모델·도구 호출 목록·최종 산출물·실패 사유를 한 묶음으로 기록합니다. 세션은 단순한 대화 이력이 아니라 하나의 업무 트랜잭션입니다. 예를 들어 AI/ML 트렌드 스캐너라면 동일한 실행 안에서 후보 수집, canonical URL 확인, 중복 판정, 캐시 업데이트가 어떻게 이어졌는지 재현할 수 있어야 합니다.

### 2. 도구 호출에 최소 권한과 멱등성을 넣기

도구 설명만 잘 쓰는 것으로는 충분하지 않습니다. 읽기 도구와 쓰기 도구를 분리하고, 쓰기 도구에는 입력 스키마·허용 경로·중복 키를 명시해야 합니다. 캐시 갱신은 임시 파일에 먼저 쓰고 JSON 파싱을 통과한 뒤 원자적으로 교체하는 방식이 기본입니다. 동일한 실행이 재시도되어도 같은 항목을 두 번 게시하거나 같은 파일을 중복 커밋하지 않도록 topic key와 파일명을 멱등 키로 사용합니다.

### 3. 토큰 사용량을 비용이 아니라 품질 신호로 보기

GitHub Copilot 웹의 세션·메시지별 토큰 사용량 표시가 중요한 이유는 비용을 보여줘서만이 아닙니다. 특정 도구가 지나치게 긴 결과를 반환하거나, 에이전트가 같은 검색을 반복하거나, 실패 후 전체 컨텍스트를 재전송하는 문제를 드러내기 때문입니다. Hermes/리오 크론에서도 실행별 입력 토큰 추정치, 도구 출력 크기, 재시도 횟수, 처리 시간을 기록하면 비용과 안정성의 상관관계를 확인할 수 있습니다.

### 리오식 최소 운영 게이트

무인 실행을 자동 승인하기 전에 다음 네 가지를 회귀 테스트로 고정합니다.

1. **출력 계약** — 필수 필드, 한국어 형식, `[SILENT]` 같은 침묵 토큰을 정확히 지키는가
2. **도구 계약** — 허용된 경로와 인자만 사용하고, 외부 부작용 도구를 임의로 호출하지 않는가
3. **장애 폴백** — 403, 타임아웃, 빈 응답을 “데이터 없음”으로 오인하지 않고 캐시나 공식 원문으로 전환하는가
4. **재실행 안전성** — 같은 입력을 다시 처리해도 중복 게시·중복 주문·중복 파일 생성이 없는가

정상 사례만 통과한 에이전트는 아직 운영 준비가 끝난 것이 아닙니다. 잘못된 JSON, 오래된 URL, 권한 오류, 도구의 부분 실패를 넣어도 같은 업무 경계를 지키는지 확인해야 합니다. 모델이 교체되거나 프롬프트와 도구 스키마가 바뀔 때마다 이 세트를 다시 실행하는 것이 좋습니다.

에이전트 자동화에서 가장 비싼 장애는 모델이 틀린 답을 한 번 생성하는 것이 아니라, 틀린 상태를 정상 상태로 기록하고 다음 실행이 그 오류를 신뢰하게 만드는 것입니다. 따라서 Hermes/리오의 실행 표면은 세션·도구·토큰·캐시를 함께 관측하고, 실패를 명시적으로 분류하는 방향으로 진화해야 합니다.
